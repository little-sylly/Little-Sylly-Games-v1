# Pecking Order (PKO) — Implementation Notes

**Spec:** `docs/new-game-tech-pecking-order.md` (Stage 2 confirmed 31 July 2026)
**Brief:** `docs/new-ideas/new-game-brief-pko.md` (v7)

---

## Design Decisions

**DD-21 — Small Fry: the opener rule ships as a three-way setting, not a hardcoded rule. [Playtest round 1]**
Playtest feedback wanted the opening Stake of a fresh game constrained to the player's smallest animal (quantity still free). Two readings were live — *the very first Stake of the Match* vs *the first Stake of every Clash* — and both are defensible, since a Clash is a fresh deal. Rather than pick one and re-litigate it after the next playtest, it ships as `pkoStartSmall`: `Off` / `Match Start` (default) / `Every Clash`. Named **Small Fry** — on-theme for a food chain, and the plain-English description carries the actual rule per the Settings Card Standard.
The rank ladder is an explicit const (`PKO_PREY_RANK`), **not** derived from `beaten_by`. The chain contains cycles — Bee beats Elephant, Orca⇄Stingray is a closed pair — so it has no well-defined depth and any derivation would be a lie that happened to work. Land and sea are parallel ladders, so Mouse and Fish are both rank 1 and either satisfies the rule. Bee, Eagle, Stingray and the Poacher are deliberately **unranked**: they sit outside the size ladder, so they neither force the rule nor satisfy it. A Hoard holding *only* unranked cards returns `null` (unconstrained) rather than an empty set — without that carve-out such a hand could not open at all and the Encounter would deadlock.
Enforced in three places, matching the existing same-species/Poacher pattern: the tap (refuse + shake, plus the barred species render greyed so the constraint is visible *before* the tap), the client submit gate, and the host's re-validation against its own mirror. The host check is the one that decides — a client could otherwise skip its own gate.

**DD-22 — The species group is the tap target, not the card. [Playtest round 1]**
Consequence of the overlap fan (DD-23). At the tightest stride a single card exposes ~7px — far under a thumb — so per-card tapping stopped being viable. Since duplicates are genuinely interchangeable (one Mouse is as good as the next), the group became the target and a tap **cycles** the staked count 0 → 1 → … → N → 0. The Stake button already read `Stake 2 × Mouse`, so the feedback for a counting model was already in place. In the Challenge builder the same tap spends the group's first *uncommitted* copy.
`pkoStakeSel` and `pkoDraft` still hold fan **positions** (DD-12/DD-16 unchanged) — only the input gesture changed, not the coordinate system. The selected copies are the group's *last* positions, because those are the ones painted on top, so the lift is always visible. One knock-on: `pkoShakeFan(pos)` indexed `el.children[pos]`, which grouping breaks — it now queries `[data-pos]`, since a card's fan position is no longer its DOM index.

**DD-23 — The Hoard fan overlaps on a measured layout instead of scrolling. [Playtest round 1]**
A flat `gap-1.5` fan of 15 cards is ~1000px inside a ~310px column, so the hand was a long horizontal scroll and you could never see it at once. Cards now overlap: **heavily within a species** (~0.20 × card width — duplicates only need to signal "there are several") and **lightly between species** (~0.64 × — each species must stay identifiable at a glance). If the ideal strides still don't fit, both shrink together toward a floor (0.10 / 0.26), so the fan fits the column rather than scrolling. Worst realistic case (15 cards, 14 species) lands at ~305px.
Two details that are load-bearing rather than incidental: the card width is **read from the rendered DOM**, not from the CSS constant, so a stylesheet change can't silently desync the maths from the render; and every card gets an explicit inline `z-index`, because `opacity` on a dimmed card creates its own stacking context and without one a spent card paints over the live card to its right. `overflow-x-auto` stays on the container as a last-resort safety valve for very narrow devices rather than clipping. If measurement happens while the screen is still `display:none` (`clientWidth === 0`) the layout re-runs once on the next frame.

**DD-24 — The Watering Hole becomes visible, and inherits the Trail. [Playtest round 1]**
`pkoWateringHole` existed from the scaffold, was written in three places, and was **never read, never rendered, never broadcast** — a discard pile only the host knew about. It now sits leftmost in the Active Marks row (spent cards on one side, live board on the other) as a face-down pile with a count, and tapping it opens a two-tab overlay: *Trail* (the existing log) and *Discards* (every spent card, grouped with ×N). The standalone "The Trail →" link is retired — the pile is the log's home.
It is broadcast in `PKO_BOARD` / `PKO_UNCHALLENGED` / `PKO_ENCOUNTER_BEGIN` / `PKO_CLASH_BEGIN` (the last at its `[]` reset value, per the accumulator rule). **No privacy cost:** every card in the pile was face-up on the board before it landed there, so this leaks nothing the players haven't already seen. It is the one piece of card *content* PKO sends on the public channel, and that is deliberate.

**DD-25 — The chain diagram finally has a call site. [Playtest round 1]**
`data/art/pko/img/chain.jpg` shipped with the core art pack (DD-05) and `assetExtra()` was built to resolve it, but the pair had **zero call sites** — the Chain overlay was a text list only. The overlay is now tabbed: **Diagram** (default) | **Animals**. Both are kept because they answer different questions — the diagram gives the shape of the ecosystem at a glance, the list gives an exact per-card `beaten_by` reading. Tap-holding a *card* opens straight to **Animals**, scrolled to that entry, because a highlighted row is the entire point of that entry path; the `[?]` and button entries open on Diagram.

**DD-01 — The interstitial ships without chrome (deliberate `ui-style.md` exception).**
`screen-pko-unchallenged` has no speaker button, no `[?]`, and no ✕. `ui-style.md` § Global UI Protocol said every screen must carry all three. The screen exists for 2.5 s, auto-advances, and has no interactive element at all; chrome on it would be tappable for less time than it takes to aim. Spec §2 specified it this way ("*no chrome — brief interstitial*"). If the auto-advance is ever made dismissible or extended, the chrome goes back on.
**No longer an exception — it is now the rule (July 2026).** `ui-style.md` § Global UI Protocol item 5 (*Interstitial exception*) covers this case explicitly and names this screen as the reference, so it should read as compliant at the Phase-Gate audit rather than as drift. See TG-01.

**DD-02 — The inert Sylly Mode toggle is shipped live, not hidden.**
Force of Nature is Phase 2, so `pkoSyllyMode` is wired to state, to `mpSerialiseSettings`, and to `playSyllyOn()`/`playSyllyOff()`, but **nothing branches on it**. This was the owner's explicit call (spec §16 Q7) against the spec's own recommendation: the app isn't live, nobody is playtesting an inert control, and FoN follows shortly. Documented exception to the "omit a control that does nothing" instinct — also flagged for the Phase-Gate audit.

**DD-03 — Card art filenames don't match chain ids; the *manifest* owns the mapping.**
`data/pko/` shipped with `poacher.png` (chain id `human`) and `polarbear.png` (chain id `polar_bear`). This was briefly a `PKO_ART_FILE` lookup table in `pko.js`; it was deleted when the core art tier landed (DD-05) — `data/art/pko/pack.json` maps id → filename, which is exactly what a manifest is for. **Never reintroduce an art-path table in a plugin.**

**DD-05 — Default art ships as a core art pack, and it's JPEG not WebP.**
`data/art/pko/` (manifest + 17 images) is the first core art pack — see the decision-log entry for the architecture. Two build-time realities shaped it: (1) there is no `cwebp`, ImageMagick or `sharp` on the machine and the project forbids npm, so conversion went through PowerShell + `System.Drawing`, which has no WebP encoder. The art is full-bleed with no transparency, so JPEG costs nothing visually and the manifest keeps the format swappable. The agreed **40 KB/card ceiling was the real constraint** and it holds — quality is walked down per-file until each fits (worst case `bee.jpg` at q68, which is the busiest image and still reads fine). (2) Cards draw at 68×92 CSS px, so 360 px wide is ~1.5× a 3×-DPR render — generous headroom without paying for it. 26 MB → 682 KB.
`mimic.jpg` is included in the manifest even though the Mimic card doesn't exist until Force of Nature (Phase 2). It costs 25 KB of precache and removes a future gotcha. The chain diagram is a non-card `extras` entry at 800 px / 141 KB — it's read, not glanced at.

**DD-06 — The Poacher test comes FIRST inside `pkoBeats()`, before any chain lookup.**
`pkoBeats(markId, cardId)` returns `true` on `cardId === PKO_POACHER_ID` before it touches `pkoBeatenByMap`. Ordering is load-bearing, not stylistic: spec §16 Q1 resolved to option (a), where a Poacher played in a Challenge stays on the board as a Mark with an empty `beaten_by`. A chain-first implementation would make that Poacher-Mark permanently unanswerable — including by another Poacher — because the lookup returns nothing and the wildcard branch is never reached. Poacher-first means the existing rule text ("wins any one Mark outright") clears a Poacher-Mark with no special-case branch anywhere.

**DD-07 — `pkoLoadChain()` awaits `artReady`; the load fires on lobby entry, not at boot.**
Core art resolves asynchronously at boot in `js/lib/art.js`, so a render that beats it to the finish shows the emoji fallback and never re-renders — a visible one-off flash on the first Hoard. `pkoLoadChain()` awaits `artReady` after parsing the chain, which costs nothing (the promise is usually settled by then) and removes the race. `artReady` never rejects — art.js catches internally — so a missing image cannot block the game. The call site is the `#btn-pko` lobby-entry handler rather than `DOMContentLoaded`: the chain overlay is reachable from the game menu before any Match exists, so the chain must be loaded by then, but users who never open PKO shouldn't pay the fetch. Idempotent guard (`if (pkoChain) return;`) makes the later call from `pkoStartSession()` free.

**DD-08 — `Math.ceil(1.5 * n)` for the Eagle is asserted, not just commented.**
Eagle is the only non-integer copy formula, and at n=3 the value is a knife-edge: `Math.round(4.5)` also gives 5, so a "tidy" to `round` passes a casual 4-player playtest and silently changes n=5 (7.5 → 8 either way) and any future formula. `tools/verify-pko-chain.js` pins the Pool totals at 110/146/183/219 and the Eagle count at 5/6/8/9, so the change is caught by a command rather than by review.

**DD-09 — Chain verification is a repo tool, not a throwaway.**
`tools/verify-pko-chain.js` evaluates the real `js/games/pko.js` in a Node `vm` sandbox with stub `document`/`fetch`/`shuffle` and asserts the four chain invariants, the Poacher wildcard, the absence of a track check, and the Pool arithmetic — 34 checks, non-zero exit on failure. It re-implements nothing, so it cannot drift from the shipped code. **Gotcha for anyone extending it:** `let` declarations inside a vm-evaluated script create lexical bindings, *not* properties on the context object, so `sandbox.pkoChain` is `undefined` while `sandbox.pkoBeats` (a `function` declaration) works. The script appends a small accessor bridge to the source to reach the state. Re-run it after any chain or balance edit, and especially when Force of Nature adds the Mimic.

**DD-10 — The client's post-lobby home is the real deal screen in an empty state, not a standby screen.**
Spec §11 has `onPassThePhone` return every device to `screen-pko-menu` with a dual-context Play CTA, but that leaves a client sitting on a live "Enter the Wild" button that must not do anything — the exact greyed-dead-control problem §16 Q7 rejected elsewhere. GTH and FLW, the two most recent MDLM games, instead start straight from `onPassThePhone` and leave clients waiting. PKO follows them: host → `pkoStartSession()`, client → `pkoShowClientStandby()`, which shows `screen-pko-hoard` with an empty fan, the Ready button hidden and "Waiting for the host to deal…". No new screen, no dead button, and `PKO_HAND` simply fills the screen the player is already looking at. The Play CTA keeps its dual-context branch for the pre-lobby path.

**DD-11 — One `pkoRenderFan()` serves both the deal screen and the table.**
The Hoard appears twice (`#pko-hoard-fan`, `#pko-my-fan`) with identical content and sort order. Two render paths would drift the moment sorting or a `pkoRenderCard` option changed, so both go through `pkoRenderFan(el, opts)` over `pkoSortHoard()`. Sort is chain order from the data file — land chain, sea chain, Poacher last — so a player's fan reads the same way the chain overlay does.

**DD-12 — Stake selection is by fan POSITION, not by card id.**
`pkoStakeSel` holds indices into the *sorted* fan, not card ids. A Hoard routinely holds four Mice, so an id-keyed selection cannot distinguish "the second Mouse" from the first, and toggling one would toggle all of them. Every place the fan is read — render, toggle, submit — maps through the same `pkoSortHoard(pkoMyHoard)` so the positions always mean the same thing. The *packet* still carries ids only (`PKO_STAKE { cards }`), so nothing position-dependent crosses the network.

**DD-13 — `.shake` is a trap; PKO has its own one-shot `.pko-shake`.**
Spec §7 asks for a shake on an illegal card tap. The obvious class, the global `.shake` in `css/styles.css:1283`, is `animation: shake 0.55s ease-in-out **infinite**` — it exists for a persistent tremor (GTH's canvas jiggle), and using it for rejection feedback leaves the card shaking until the next re-render. Added `.pko-shake` (0.35s, one shot) modelled on `.shp-shake`, which exists for the same reason. **Anything reaching for a "shake" in this codebase should check the iteration count first.**

**DD-14 — Only the host schedules the Unchallenged auto-advance.**
`pkoShowUnchallenged()` returns early before setting `pkoUnchallengedTimer` when this device is a client. Both devices showing the interstitial and both counting down to `pkoStartEncounter()` would have the client racing a state transition it has no authority over. Clients leave the screen when `PKO_ENCOUNTER_BEGIN` arrives — and that handler clears the timer defensively anyway, as do `PKO_CLASH_END` and `PKO_MATCH_END`, so a late SYNC can never fire an advance into the wrong screen.

**DD-15 — Every board change funnels through `pkoAfterBoardChange()`.**
Stake, Challenge and Stampede all end identically: check whether the player just emptied their Hoard (Clash end fires *before* the board resolves, §6), otherwise reset `pkoRetreatedSince`, restart the response window clockwise from the player who changed the board, broadcast, re-render. Writing that tail three times is how one of the three silently forgets to forgive Retreats — the bug that turns a Retreat into a lock-out. Same instinct as `pkoBeats()`: one place, three callers.

**DD-20 — The turn loop gets its own harness, because MDLM makes it untestable by hand.**
`tools/verify-pko-loop.js` plays all four seats through the real host appliers in one Node process — 75 checks covering Stake, Challenge, Stampede, Retreat, the response-window reset, Encounter end, Clash end, Match end, and every rejection path in the host's re-validation. It works because of a property worth protecting: **the appliers take an explicit `playerIdx` and skip every broadcast in `'single'` mode**, so a single process can be all N players. Two sandbox details matter — `setTimeout` is *captured, never fired*, so the Unchallenged interstitial's 2.5 s advance is stepped deliberately by the test (and its scheduling is itself asserted); and `mpSendEnvelope`/`mpSendPrivate` **throw** rather than no-op, so a broadcast leaking into single-device mode fails loudly instead of passing silently. Same `vm` bridge gotcha as DD-09 (`let` bindings are invisible from outside; the appended bridge exposes them). Found BUG-01 on its first run. **Re-run both tools after any change to the appliers, the chain, or the balance numbers.**

**DD-16 — `pkoDraft` holds fan POSITIONS, not card ids (spec §4 says ids — deliberate departure).**
Same reason as `pkoStakeSel` (DD-12), and the spec's own §4 wording predates that decision. A Hoard routinely holds four Mice, so an id-keyed draft cannot express *which* Mouse is committed: dimming "the used card" in the fan would dim all four, and un-assigning one would be ambiguous. Positions index the *sorted* fan, and every read — render, tap, submit — goes through the same `pkoSortHoard(pkoMyHoard)`, so a position means one thing everywhere. The **packet is unaffected**: `pkoSubmitChallenge` maps positions → ids at the wire, so `PKO_CHALLENGE { assignments }` carries ids only and nothing position-dependent crosses the network. The checklist item "`pkoDraft` is a flat array, never nested" still holds — it is flat, just of positions.

**DD-17 — Un-assigning is done by tapping the SLOT, never by re-tapping the card.**
A committed card renders dimmed and inert in the fan. The alternative — tap the dimmed card to return it — is ambiguous the moment two slots hold the same species: tapping "a used Mouse" cannot say which slot to empty. Tapping the slot is unambiguous by construction, and the slot stays armed afterwards so a swap is one further tap. This is why Method A and Method B only ever *assign*.

**DD-18 — Card assignment uses `playPillClick()`, not `playSuccess()`.**
Spec §9 asks for "`playSuccess()` — subtle variant". No subtle variant exists, and `playSuccess()` is a bright three-note chime — on a six-wide board that is six chimes to build one Challenge. `playPillClick()` is this codebase's established light-tick confirmation and is what "subtle variant" was reaching for. `playSuccess()` is left for outcomes, not for building.

**DD-19 — The Challenge Confirm button carries a progress label, not just a disabled state.**
A Challenge is all-or-nothing, so Confirm is disabled until `pkoDraft.every(v => v !== null)`. A permanently-greyed button with no explanation is the "greyed dead control reads as a bug" problem §16 Q7 rejected elsewhere, so while incomplete the label reads `N of M answered` and only becomes `Confirm` when the draft is complete.

**DD-21 — Swarm was restored by changing its shape, not by overruling the reason it was cut. [Playtest round 2, July 2026]**
Brief v6 cut per-slot Swarm on the strength of `pko_log1.md` blocker #1: *"a slot holds Mongoose ×2 — does one Leopard beat it, or do you need two? Both are defensible, and they're very different games."* That is a real, unresolvable-by-fiat ambiguity — **but it only exists if a slot can hold depth.** The restored design makes a Swarm's two cards become **one Mark each** the instant they land, so `pkoMarks` stays flat, a slot always holds exactly one card, and the question can never be asked. The invariant v6 was protecting (`pkoMarks` "ALWAYS one id per Mark, never nested") is untouched.
Two things worth carrying: **(a)** the cut also took out one of only two outlets `pko_log1.md` item F named for shedding Mouse/Fish — *"a Stake or a Swarm"* — and item F was explicitly deferred to playtest rather than redesigned. Round 2 returned the verdict: the remaining single outlet was not enough, and the stall it predicted is exactly what the table felt. **(b)** **Mob** — several cards answering one Mark and *staying* stacked — is the idea that actually created the depth-parity problem, and stays cut. Swarm and Mob were conflated in the v6 discussion; separating them is what made the restoration possible.
*Lesson:* when a mechanic is cut over an ambiguity, record **the ambiguity**, not just the verdict. "Swarm is cut" survived into the brief; "because slots would gain depth" did not, so the cut looked like a judgement about Swarm rather than about one implementation of it.

**DD-22 — Board growth was already a shipped mechanic, which is what makes Swarm safe.**
`pkoSubmitStampede` plays exactly `pkoMarks.length + 1` and returns the board one Mark wider. Swarm is the per-slot version of that, so it inherits the same self-limiting property: every Swarm makes the *next* answer harder, so Encounters close faster rather than spiralling. Swarm is capped at exactly 2 for the same reason Stampede is capped at exactly N+1 — an uncapped Swarm would let a player dump five cards onto one Mark and build a board nobody can answer. The two mechanics coincide on a 1-Mark board and diverge on wide ones (a 3-board costs 4 cards by Stampede, 6 by Swarming every slot); both were kept.

**DD-23 — Appetite ships defaulting to Sated so round 3 can attribute the fix.**
Swarm and the Ravenous two-tier chain both attack the same round-2 symptom by different routes: Ravenous widens *who* can answer, Swarm widens *how*. Shipping both on would have made round 3 unattributable — and if it overshot, there would be no way to know which lever to pull back. Swarm is the stronger candidate (it fixes the observed mouse/fish stall directly) so it ships as a core rule against the known baseline chain; Appetite ships fully built but **off**, as a free table-side A/B (flip mid-session, no rebuild, no extra playtest round). *Choosing which of two good fixes to ship ON is a measurement decision, not a design one.*

**DD-24 — Two predicates, not one: `pkoAnswers` for legality, `pkoSlotAccepts` for building.**
Swarm creates a state the old model had no room for: a slot holding one card that does *not* answer its Mark but is a legal half of a Swarm. Folding that into `pkoAnswers` would have made "is this Challenge submittable?" and "may this card sit here?" the same question, and they are not — the first gates Confirm and host re-validation, the second only gates a tap. Keeping them separate is what lets a half-built Swarm render as a dashed, explicitly-unanswered slot with a prompt, instead of silently counting as done. Only `pkoAnswers` crosses the wire.

**DD-25 — The fan's height is computed, not fixed; and the rotation is what caused the scrollbars.**
Two findings from fanning the hand, both about `transform: rotate()` **not changing the layout box while still creating visual overflow**. (a) *Horizontal:* the stride maths fitted the row exactly, but the painted fan swept wider — and both fan containers are `overflow-x-auto`, so the browser added a scrollbar the arithmetic said shouldn't exist. `pkoLayoutFan` now reserves the real sweep, `2·H·sin(span/2)`, instead of a guessed constant, and the strides tightened (`0.20W→0.16W` within species, `0.64W→0.50W` between) because the rotation itself now supplies the group separation the wider gaps used to. (b) *Vertical:* the arch peak scales with card count, so a fixed `min-height` either clips the fan or leaves dead space. The height is now computed from the layout just performed — `H + H(1−cos θ) + (W/2)sin θ + arc sag + lift`. *Lesson: when a layout function applies transforms, it owns the container's dimensions too — CSS cannot know the geometry the JS just chose.*

**DD-23 update — the Sated default paid for itself immediately. [July 2026]**
One Sated + Swarm session was enough for the owner to conclude the two-tier reach probably isn't needed and to keep Appetite as a variant. That judgement was only available *because* Appetite shipped off: with both levers on, "it flows better now" would not have been attributable to either. Keeping Ravenous costs nothing (already built, harness-covered under both modes) and it stays as the large-table option. **Caveat for round 3:** the supplied Trail contains **zero Swarms** — every `×2` in it is two Marks answered one-for-one, since `pkoSummariseCards` groups duplicates and the `— N Swarms` suffix never appears. BUG-05 made mixed selection from the hand impossible during that session, pushing players into the builder or simpler plays, so that log is **not yet evidence about Swarm's value**. Re-read the Trail after BUG-05 ships before drawing any conclusion.

**DD-04 — Settings pills were wired during the scaffold, not deferred to Step 5.**
Protocol B Step 5 says "settings last". The pill/toggle handlers are pure UI state with no gameplay coupling, and leaving them dead made the Step 3 flow walk untestable — a settings overlay whose controls don't respond can't be distinguished from one that's broken. Ten lines, wired early, noted here.

## Bug Index

**BUG-05 — a mixed answer was impossible from the table fan, though the builder accepted it. [Playtest round 2 follow-up, July 2026]**
*What happened:* board of 3 × Fish. Tapping Mongoose, Mongoose, Octopus from the hand was refused; so was Octopus first. The Challenge *builder* handled both orders fine.
*Root cause:* **self-inflicted, in the same slice that added quick play.** Quick play was built by reusing the Stake's group-cycling (`pkoCycleStakeGroup`), which carries `if (current && current !== grp.id) return refuse();` — *"mixed species — refuse the tap"*. That is a correct **Stake** rule (§7: "A Stake is one species only") and a wrong **Challenge** rule. `pkoQuickPick()` then compounded it with `new Set(cards).size !== 1`. The builder was unaffected because it never touches `pkoStakeSel` — it uses `pkoDraft`, and `pkoAutoFillSlot` assigns each card to the leftmost Mark it legally answers.
*Fix:* the two selections are now separate models by construction — `pkoStakeSel` (flat, one species) for a Stake, `pkoDraft` (per-Mark, freely mixed) for a Challenge. The table's answer path is `pkoCycleAnswerGroup`, which calls the **builder's own** `pkoAutoFillSlot` with a `containerId`. `pkoQuickPick`/`pkoSubmitQuickChallenge` are deleted; the Challenge button commits when `pkoDraftComplete()` and otherwise opens the builder *carrying the partial draft in* (`pkoOpenChallenge` now only re-arms a **stale** draft). Swarms became reachable from the table for free, since `pkoAutoFillSlot` already prefers completing a started Swarm.
*Lesson:* **reusing a UI interaction across two game actions silently imports that action's rules.** The cycling *gesture* was right to reuse; the state model behind it was not, and nothing in the code said which of `pkoCycleStakeGroup`'s guards were about the gesture and which were about Stakes. Where one widget serves two actions, either the shared part must hold no rules at all, or the two paths must be separate functions. They are now, and both carry a comment naming the other.
*Why nothing caught it:* the loop harness covered the appliers and the builder's draft functions, but **the table tap path had zero coverage** — it was UI-layer, so it looked out of scope. It isn't: `pkoCycleAnswerGroup` → `pkoAutoFillSlot` is rules logic wearing a UI hat, and every render call it makes is DOM-guarded, so it runs unmodified in the harness sandbox. §12 of `verify-pko-loop.js` now drives it directly (mixed answers both orders, the wrap-release cycle, a table-built Swarm, an illegal tap). *If a function decides what is legal, it belongs in the harness regardless of which layer it lives in.*

**BUG-03 — Retreat and Stampede labels sat top-left. [Playtest round 2, July 2026]**
*What happened:* the Retreat button's label was visibly not centred; Stampede had it too.
*Root cause:* `pkoRenderTable`'s visibility helper reveals every table action with `el.style.display = 'flex'`. `#btn-pko-stake` and `#btn-pko-challenge` survive that because `.pko-cta` declares `display:flex; align-items:center; justify-content:center`. Stampede and Retreat use plain Tailwind colour utilities and carried **no centering utilities at all**, so `display:flex` gave them the flex defaults — `align-items:stretch; justify-content:flex-start`.
*Fix:* added `flex items-center justify-center` to both.
*Lesson:* `logic-engine.md` already carried this rule, but scoped to **custom brand CSS classes** — which is why these two were missed: their colour comes from ordinary Tailwind utilities. The real rule is broader: **any button a script reveals with `style.display = 'flex'` needs the centering utilities, whatever its colour comes from.** Elevated.

**BUG-04 — "a Fish can't answer a Fish" presented as a dead button. [Playtest round 2, July 2026]**
*What happened:* reported as "you still can't swarm a Mark — it won't let me select the same species even when I have two". Board was `[fish, fish]`; the player tapped Fish and nothing happened.
*Root cause:* **not a defect.** Verified headlessly: no species beats itself, Fish is beaten by Mongoose/Eagle/Octopus/Poacher, and answering a 2-Fish board *with Fish* requires **three** (Stampede's N+1), not two. The builder was correct. Three things conspired to make correct behaviour read as broken: (1) spec §7 specified the per-slot rejection as *silent* — a shake, no reason, no alternative; (2) `pkoCanStampede()` false meant the Stampede button was **hidden entirely**, so the N+1 rule was invisible at exactly the moment it applied and a player could finish a match never learning the action exists; (3) every climbing game the table already knows (Big 2, Tichu) lets you match-and-beat, so the instinct is strong and was silently punished.
*Fix:* rejections now name the rule and the alternative, derived from `pkoPredators()` so the help cannot drift from `pkoBeats`. Stampede is shown **disabled with its price** on a uniform board and hidden only on a mixed board where it can never apply. Spec §17 D10.
*Lesson:* **a silent rejection is only safe when the rule is already obvious to the player.** Where a game deliberately contradicts a genre convention, the refusal has to teach — otherwise the correct implementation is indistinguishable from a broken one, and the bug report you get back is about the wrong thing. This one also inflated the round-2 "too much passing" complaint independently of the chain: players were almost certainly Retreating on boards where a Stampede was legal and never saw the button.

**BUG-02 — a client's Hoard was never repaired after it played, so every card it played stayed in its fan and became unplayable. [Playtest round 1, 31 July 2026]**
*What happened:* first three-device playtest. A client Staked 2 × Mouse and went Unchallenged. The two Mice were still sitting in that player's fan afterwards, its own count chip disagreed with its fan, and tapping those Mice on a later turn did nothing at all — no error, no shake, the board just bounced back unchanged.
*Root cause:* `pkoRemoveFromHoard()` removed the cards from `pkoHoards[playerIdx]` — the host's authoritative mirror — and then repaired the local `pkoMyHoard` only via `if (playerIdx === pkoMyIdx()) pkoMyHoard = hoard;`. On the host device `pkoMyIdx()` is the *host's own* seat, so that line fires only when the host is the actor. When a **client** played, nothing was sent to that client about its own cards: `PKO_BOARD` carries `hoardCounts` but never contents (correctly — contents are private), and a client's `pkoMyHoard` was otherwise only ever written by the initial `PKO_HAND` deal. The client's hand was therefore frozen at the deal for the whole Clash. Re-playing a ghost card then failed `pkoHoldsAll()` inside the host's re-validation, which drops the ACTION silently and rebroadcasts the board — by design, and exactly what made this look like a dead button rather than a desync.
*Fix:* `pkoRemoveFromHoard()` now sends the acting player their **whole authoritative hand** down the private channel as `PKO_HAND_SYNC` whenever the actor isn't this device. A full replacement rather than a delta, so a dropped packet self-corrects on the next play. The handler deliberately does **not** call `mpUnlockSync()` — the paired `PKO_BOARD` owns the unlock, and releasing early would reopen the double-tap window. It is a separate action from `PKO_HAND` because that handler renders the deal screen, and this one arrives mid-Encounter.
*Lesson:* **in a private-hand game, every mutation of the host's mirror of a hand needs a matching private packet to that hand's owner — the public board packet cannot carry the repair, because the whole point of the private model is that it carries counts only.** Putting the send inside `pkoRemoveFromHoard` (rather than in each of Stake / Challenge / Stampede) is what makes it exhaustive: there is one place a card can leave a Hoard, so there is one place the repair can be forgotten.
*Why the harness missed it:* `tools/verify-pko-loop.js` runs in `'single'` mode, where `pkoMyHoard` is an **alias** of `pkoHoards[0]` — the same array object — so a per-seat mirror bug is invisible to it by construction. This is not a harness defect; it's the boundary of what a single-process harness can see. The general guard added in response is a **card-conservation census** (`Σ hoards + marks + reserve + wateringHole` is invariant across every applier), which catches the adjacent class of bug — a card that leaves a Hoard without arriving anywhere — even though it cannot catch this exact one. See TG-07.

**BUG-01 — `pkoEndEncounter()` left the board standing for 2.5 s, so a late Retreat resolved the Encounter twice.**
*What happened:* `pkoEndEncounter()` pushed `pkoMarks` to the Watering Hole but never cleared it — the board was only reset 2.5 s later by `pkoStartEncounter()`, fired from the Unchallenged interstitial's timer. Inside that window `pkoApplyRetreat()`'s guards (`playerIdx === pkoTurnIdx && pkoMarks.length`) both still passed, because the turn index is not advanced when an Encounter ends either. A `PKO_RETREAT` a client submitted just before the Encounter closed therefore ran the whole ending again: marks pushed to the Watering Hole a second time, a duplicate Trail entry, the interstitial re-shown and its advance re-scheduled — two timers racing toward `pkoStartEncounter()`.
*Root cause:* the end-of-Encounter state change was split across two functions 2.5 s apart, leaving a window where the board looked live but the Encounter was over. Exactly the cascade `logic-engine.md` warns about under *Firebase callback crash safety* — buffered events re-delivered against partially-reset state.
*Fix:* `pkoEndEncounter()` captures the winning board into a local (`won`, used for the display and the SYNC payload) and clears `pkoMarks` immediately. An empty board is then the guard that drops the late ACTION. The client's `PKO_UNCHALLENGED` handler clears `pkoMarks` too, so both sides mirror.
*Lesson:* **when a phase ends, every piece of state that gates entry to that phase must be cleared in the same synchronous step — never on the timer that shows the next screen.** An interstitial's delay is UI time, not state time. Found by `tools/verify-pko-loop.js`, not by review: the loop test's "keep Retreating until the board clears" termination check never terminated.

## Multiplayer Lessons

**ML-01 (pre-emptive, from the spec's highest-risk item) — the host is a full player.**
PKO's host can Stake, Challenge, Stampede, Retreat, and confirm ready. `engine-multiplayer.js` drops every envelope where `originId === syllyDeviceUid`, so any of those five sent by the host via `mpSendEnvelope({type:'ACTION'})` vanishes silently and the round hangs. All five must branch: host mutates state directly then broadcasts the SYNC; `type:'ACTION'` is reserved for clients. Already shipped as a bug in NT (`NT_ALLOCATION_UPDATE`), JEC and YGI — this game was specced with the fix in hand, so if it appears here anyway it means the branch was dropped during injection, not that the pattern was unknown.

**ML-02 — PKO was missing from `MP_GAME_CONFIGS` entirely until the lifecycle slice.**
Protocol B Steps 2–4 delivered the scaffold, screens, routing and exits, and everything *looked* complete — the menu opened, settings worked, exits routed. But `js/engine-multiplayer.js` had zero occurrences of `pko`: no config entry, no `mpSerialiseSettings` case, no settings-apply case, no envelope routing. Nothing in the game surfaces that gap until the moment a lobby is created, which is well past the point Steps 2–4 declare "flow verified". **Lesson:** for an MDLM-only game, "routing verified" in Step 4 means the *pre-lobby* path only. Add a one-line grep — `grep -c "<abbr>" js/engine-multiplayer.js` — to the Step 4 exit criteria; a zero there means the game cannot start a session no matter how good the screens look.

**ML-04 — Two of the six ACTION handlers were missing, and nothing surfaced it.**
`PKO_CHALLENGE` and `PKO_STAMPEDE` had no `case` in `pkoHandleEnvelope`'s ACTION switch until the appliers were written — the scaffold wired the buttons, stubbed the appliers, and left the switch with four of six branches. A missing handler does not error: the envelope arrives, matches nothing, and is dropped, so a client's Challenge would simply never happen and the round would hang on a player who had already submitted. This is the same failure mode the spec's own §11 audit table exists to prevent, and the table was green (see TG-06). **The handler and its applier must be written in the same edit** — a stubbed applier with a live button is a handler that looks present and isn't.

**ML-05 — A client's in-flight ACTION can arrive after the phase that accepted it has closed.**
BUG-01's real shape: the guards on `pkoApplyRetreat` were correct for the *current* board, but the board outlived the Encounter by 2.5 s, so a Retreat sent legitimately (the client tapped while it was still their turn) arrived legitimately and was applied into a phase that no longer existed. In MDLM there is always network latency between a client's tap and the host's state, so **every applier's guards must be false the instant its phase ends, not merely by the time the next screen renders.** Clearing the phase-gating state synchronously at the end of the phase is what makes a late ACTION a no-op instead of a second resolution.

**ML-06 — The private-hand model needs a repair packet, not just a deal packet. [BUG-02]**
FLW introduced `mpSendPrivate` for dealing hands, and PKO copied that: `PKO_HAND` at the deal, `PKO_DRAW` for a Scavenge card. What neither game's pattern made obvious is that **playing** a card is also a private-hand mutation and also needs a packet. FLW never hit it because a Showing replaces the whole hand state anyway; PKO's Hoard persists across an entire Clash, so a missed repair compounds — the client's hand froze at the deal and never recovered.
The generalisable rule: **in a private-hand game, list every operation that changes a hand — deal, draw, play, discard, steal — and confirm each has a private packet to that hand's owner.** The public board packet cannot carry the repair; the whole point of the model is that the public channel carries counts only. Funnel the send through the single function where cards leave a hand (here `pkoRemoveFromHoard`) rather than repeating it per applier, so it can't be forgotten in the next one added. Send the **whole hand**, not a delta — a full replacement self-corrects if a packet is ever missed.

**ML-03 — `PKO_CLASH_BEGIN` carries every accumulator explicitly, including the empty ones.**
`hoardReady`, `retreatedSince`, `marks`, `trail`, `markOwnerIdx` and `encounterNum` are all in the payload at their reset values even though most are `[]`, `false` or `-1`. The host resets them locally when it builds the Clash; clients never do. Omitting a field because "it's empty anyway" is exactly the FLW BUG-01 failure — the client keeps last Clash's value and either shows a stale log or fires a readyCheck instantly. This is the rule elevated to `logic-engine.md` during this phase's Protocol C, applied at its first opportunity.

## Template Gaps

**TG-01 — "Every screen has speaker + ✕" has no carve-out for non-interactive interstitials. [RESOLVED — elevated July 2026]**
DD-01 above is the second time a screen has existed purely to be read for a couple of seconds. `ui-style.md`'s Global UI Protocol read as absolute, so any auditor hitting `screen-pko-unchallenged` would flag it. **Actioned:** `ui-style.md` § Global UI Protocol now carries a fifth item — an *Interstitial exception* exempting a screen that **auto-advances AND has no interactive element** from the speaker / `[?]` / ✕ requirements. Deliberately scoped to both conditions together, with an explicit reversal clause (if it ever becomes dismissible or user-paced, the chrome returns), so "it's brief" alone can't be used to strip chrome from a real screen. `screen-pko-unchallenged` is named as the reference.

**TG-02 — Bitmap art had no size gate anywhere in the process docs. [RESOLVED — elevated July 2026]**
`data/pko/` arrived at **26 MB** across 17 PNGs (~1.5–2 MB each) against the 40 KB/card ceiling confirmed in spec §16 Q6. PKO is the first game to precache bitmaps, and nothing in `new-game-process.md` or the PWA Guardian checklist asked "what does this add to the install?" before art was generated. A 26 MB precache would make the app effectively uninstallable on mobile data. **Actioned:** `logic-engine.md` § PWA Guardian now carries a fourth question — any precached binary asset needs a per-file ceiling agreed *before* generation, stated in the tech spec.

**TG-04 — Source art originals need a home outside the repo.**
`data/pko/` still holds the 26 MB of original PNGs. They are the masters — re-conversion at a different ceiling needs them — but they must never be committed. Currently untracked. Move them to the external archive alongside the phase snapshots, or add `data/pko/` to `.gitignore`. **Owner decision pending; nothing deleted.**

**TG-05 — No process doc asks a new game to verify its own arithmetic before building on it. [RESOLVED — elevated July 2026; the harness now covers the LOOP, not just the data]**
PKO's spec (§10) hands over four Pool totals and calls them "the cheapest correctness check available at Stage 3", but nothing in `new-game-process.md` or the Step 5 checklist says *how* to check them — and with no test framework in the project, the default is a browser console session that leaves no artefact. `tools/verify-pko-chain.js` (DD-09) is the answer here; the general shape — a Node `vm` harness asserting a game's data layer against the spec's own numbers, committed to `tools/` — applies to any future game with a deck, a chain, or a scoring table. Worth a checklist line in `logic-engine.md` § Adding a New Game once a second game has one.
**Actioned (July 2026):** `logic-engine.md` § Checklist: Adding a New Game now carries a **Rules-engine verification harness** item — required for any game with a deck, chain, or scoring table, and **mandatory for MDLM-only games**. It states the architectural precondition as a requirement (appliers take an explicit `playerIdx` and skip broadcasts in `'single'` mode), because that constrains how the appliers are *written*, not merely how they are tested afterwards. The method and the sandbox gotchas live in `docs/rules/new-game-process.md` § Stage 3 → *Verifying the rules engine* — kept out of the always-loaded rule file to protect the baseline context budget. Still open: the Stage 2 **tech template** does not yet ask for a harness in its §15 checklist, so each new spec must remember it unprompted.
**Update (July 2026):** `tools/verify-pko-loop.js` (DD-20) extends the pattern from the data layer to the *turn loop*, and it earned its keep on the first run by finding BUG-01 — a double-resolution that three-device playtesting would have surfaced as an intermittent "the interstitial flashed twice", i.e. the hardest possible way to find it. **This is the stronger version of the gap:** for an MDLM-only game the rules engine is unreachable from a single browser, so without a harness the first Challenge ever played is also the first time the code runs. The enabling property is architectural and worth stating in the tech template: *the host appliers take an explicit `playerIdx` and skip every broadcast in `'single'` mode, so one process can play all N seats through the real shipped functions.* A game whose appliers read `mpMyPlayerIdx` internally instead of taking a seat argument cannot be tested this way.

**TG-06 — The missing-handler audit passed on paper while two handlers were absent in code.**
Spec §11's audit table lists all six ACTION handlers with ✅ against each, including `PKO_CHALLENGE` and `PKO_STAMPEDE`. Both were genuinely missing from `pkoHandleEnvelope`'s ACTION switch until this slice — the table was ticking off *the spec's intent*, not the shipped code, because it was written before the code existed and never re-run against it. The scaffold shipped with the appliers stubbed and the table already green. **The audit is only meaningful when re-run against the implementation**; a checklist authored at Stage 2 and never re-verified at Stage 3 is a to-do list wearing an audit's clothes. Cheap enforcement: diff `grep -o "PKO_[A-Z_]*" js/games/pko.js | sort -u` against the spec's packet table as a Step 5 exit criterion — same shape as the `grep -c` fix ML-02 proposed for Step 4.

**TG-07 — A single-process rules harness is structurally blind to per-device mirror bugs.**
`tools/verify-pko-loop.js` runs in `'single'` mode, where `pkoMyHoard` is an *alias* of `pkoHoards[0]`. Every "is this device's view correct?" question therefore answers itself trivially, and BUG-02 — the host's mirror and a client's local hand diverging — was invisible to 75 passing checks. This is the harness's boundary, not a defect: one process has one device's view by definition.
Two things worth carrying to the next MDLM game. First, **state the boundary in the tech spec** so nobody reads a green harness as "multiplayer verified" — it verifies the *rules engine*, and per-device view sync is explicitly out of scope. Second, **add a conservation census** to any game with a fixed pool of tokens/cards: `Σ all hands + board + reserve + discard` must be invariant across every applier. It doesn't catch a mirror desync directly, but it catches the whole adjacent family — a card that leaves one place without arriving anywhere — and it costs four lines. Added here as §9 of the loop harness; it should be a default for any deck game.
The complementary check that *would* have caught BUG-02 is a three-device smoke path, which is why playtest round 1 found it on the first client Stake. Cheap enforcement for next time: **the first playtest action should always be a non-host player taking a turn**, since host-as-participant means the host path exercises the aliased-state happy case and proves nothing about clients.

**TG-03 — `getMuteToggleOnClass()` is missing an `'frt'` entry (pre-existing, not PKO).**
Spotted while adding `'pko'`. Fruit Salad's mute toggle falls back to neutral stone instead of its banana brand colour. Unrelated to this build; logged here because this is where it was found. One-line fix in `engine.js`.
